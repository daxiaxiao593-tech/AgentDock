用户已经同意以下建议，要求我们先讨论达成共识，再调研 GitHub 复用方案并出技术文档。此前产品：Windows 单窗口，左侧按真实目录分组，组内多个 Codex CLI、Antigravity CLI(agy)、Claude Code 会话；每次新建独立选目录，切换不停止后台。先模拟 Demo，再真实接入。现有技术候选 Electron + React + xterm.js + node-pty，但用户要求优先复用开源，不能提前锁死自研。最终用户通过桌面快捷方式打开。

新增建议：
1. 借鉴 Mitchell Hashimoto 的公开终端设计经验：复用成熟终端核心、平台使用习惯、兼容性和小而可靠的首版。这是我们基于其公开文章的推演，不声称联系过本人，不意味着采用 Ghostty 或 Zig。
2. 桌面应用单实例，重复双击唤起已有窗口，不重复启动会话。
3. 同目录多会话共享真实文件，首版明确提示、不自动创建 worktree；独立 PTY 不隔离文件、账号、额度。
4. 保存会话配置与恢复 AI 历史分开。首版自动启动已勾选的 CLI，不自动重发提示词；历史恢复先用 CLI 自带方式，将来验证后再加。
5. 运行中表示进程存活，后台新输出加未读标记；只有可靠结构化事件才标“需要处理”，不用终端关键词猜测。
6. 5000 行回滚不限制输入队列；真实版要做流量控制、后台输出压力测试。
7. 区分正常退出、渲染崩溃、主进程崩溃、睡眠/断网，不自动重试任务指令。停止时仅清理本应用的进程树。
8. 三种 CLI 升级后分别检测兼容性，一种失败不拖垮其他；Windows 缩放、中文 IME、多行粘贴、复制快捷键列入验收，图片粘贴单独确认兼容性，不默认承诺。
9. GitHub 候选评估许可证、Windows 实际路径、三 CLI 接入难度、项目树、维护与打包；优先直接复用，其次小改造，再其次复用成熟组件自建薄壳。许可及功能以仓库实际文件为证据，不只看截图/星数。

## Antigravity CLI 实际回答

作为本地 AI 终端工作台的联合设计评审者，我对上述 9 项新增建议的评审意见、调整补充及最终技术共识清单整理如下：

---

### 一、 逐项评审意见与补充

*   **第 1 项（借鉴公开终端设计经验）｜【同意】**
    *   **调整/补充**：核心是“终端作为系统级基础底座，而非简单的富文本框”。重点复用成熟的 ConPTY/xterm 流水线，保证首版吞吐和低输入延迟；UI 层保持克制，不自造虚拟终端解析引擎。
*   **第 2 项（桌面应用单实例与唤起）｜【同意】**
    *   **遗漏补充**：需补齐传参处理。二次启动若带有命令行参数（如通过右键菜单指定目录启动），应向已有主实例通过 IPC 发送“新建会话(目录)”事件并置顶窗口；若无参数，仅激活并置顶当前窗口。
*   **第 3 项（同目录多会话真实共享、独立 PTY）｜【同意】**
    *   **遗漏补充**：需增加并发写风险的视觉提醒（如标签旁显示“多会话共享目录”警告徽标）。独立 PTY 虽不隔离文件，但必须提醒用户注意 Git 锁（如两个会话同时执行 commit 导致 `.git/index.lock` 冲突）与环境配置覆盖。
*   **第 4 项（配置保存与 AI 历史恢复解耦）｜【同意】**
    *   **调整/补充**：方向正确。首版只持久化元数据（`workingDirectory`, `cliType`, `customArgs`, `env`）。坚决禁止“自动重发最后一条 Prompt”，避免产生非预期 Token 消耗或非幂等副作用。AI 会话上下文先严格依仗 CLI 原生机制（如 `claude --resume`）。
*   **第 5 项（存活状态、未读标记与状态机界限）｜【修改】**
    *   **调整建议**：坚决反对任何基于终端 ANSI 文本的正则猜测（如匹配 `[y/N]` 或 `?`），但需澄清“可靠结构化事件”的定义。Windows 首版在没有专用 hook 前，**仅保留“运行中/已退出”和“有未读新输出”两档**；除非接入各 CLI 原生 IPC/Stdio JSON 模式或标准的 OSC 终端通知协议，否则首版不做“等待用户输入”状态。
*   **第 6 项（5000 行回滚与流控压力测试）｜【修改】**
    *   **调整建议**：回滚行数合理，但“不限制输入队列”需增加边界保护——必须设置前端 IPC 与渲染批处理（batch rendering，如 `requestAnimationFrame` 节流合并输出），防止 AI 高速大段打印时阻塞 Electron 渲染主线程导致界面假死。
*   **第 7 项（故障分级与进程树清理）｜【同意】**
    *   **遗漏补充**：Windows 平台调用标准 Node `kill()` 极易残留脱壳的 `conhost.exe` 或 CLI 子进程。必须在技术方案中显式指定使用 Windows Job Objects 或调用 `taskkill /PID <pid> /T /F` 进行整棵进程树强制清理。
*   **第 8 项（CLI 独立兼容性与 Windows 本地化验收）｜【同意】**
    *   **调整/补充**：务必将 Windows 高 DPI 缩放下的光标错位、中文 IME 预选框跟随、Windows 路径中的空格与反斜杠处理列入首批冒烟用例。图片粘贴在 Windows CLI 下多数依靠保存临时文件并传路径，首版不承诺剪贴板原生二进制直传。
*   **第 9 项（GitHub 候选评估优先级与实据导向）｜【同意】**
    *   **调整/补充**：评估优先排除强传染性开源协议（如 GPL/AGPL）。重点考察候选项目的“终端引擎与 UI 框架解耦度”，如果现有开源项目架构侵入性过高，宁可选用成熟组件（xterm.js + node-pty）构建干净的薄壳。

### 二、 可直接写入技术文档的共识清单

#### 1. 已形成的设计结论（锁定项）
*   **实例模型**：Windows 桌面单实例运作。重复启动自动唤起并聚焦原窗口；支持将二次启动的 CLI 目录参数转发给主窗口。
*   **目录与进程**：多会话按目录归集展示，同目录会话直接读写真实文件系统；首版不内置 Git worktree 自动分流。停止会话时强制递归清理完整 Windows 进程树，杜绝僵尸后台。
*   **会话恢复边界**：配置持久化与模型记忆彻底解耦。仅保存会话基本环境元数据；首版绝不自动补发/重放用户历史 Prompt，由 CLI 原生方案维护多轮上下文。
*   **状态与流控基线**：状态展示严格收敛为“存活/退出”与“输出未读”。废弃正则语义嗅探；终端输出必须增加渲染缓冲节流，杜绝大文本爆流锁死 UI。
*   **体验基线**：Windows 中文输入法、DPI 动态缩放、多行代码粘贴为硬性验收指标；图片直接粘贴不作首版承诺。

#### 2. 待开源调研与 Windows 实测项（待办与验证项）
*   **开源选型裁决**：调研候选项目的开源许可证风险、目录树结构可扩展性及 Windows ConPTY 的稳定实现。在“轻度改造开源成熟客户端”与“自建薄壳组合成熟组件”间给出最终选型决策。
*   **CLI 结构化状态接口**：针对 Codex CLI、agy 和 Claude Code，逐一测试它们在 Windows 终端下是否支持 OSC 提示符标记、Stdio JSON 流或专用退出信号，判定是否有可行低成本手段实现“等待用户操作”提示。
*   **进程守护稳定性实测**：实测 Windows 系统进入休眠/恢复唤醒、断网重连场景下，底层 PTY 通道与三个 CLI 进程的存活表现与恢复机制。
