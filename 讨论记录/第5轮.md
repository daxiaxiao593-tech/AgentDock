### 一、 三类证据的严格分界

1. **本轮源码核对证据（硬事实）**
   - **参数与行为污染**：`antigravity` 适配器源码写死了 `--mode accept-edits`、`--log-file` 和自定义状态行辅助脚本；Claude 适配器存在自动确认 Hook。原样运行会直接破坏“无语义猜测、不篡改权限”的底线。
   - **状态模型冲突**：`terminal-registry.ts` 源码逻辑是“历史恢复优先（`resumed: true`）”，遇到失效目录直接丢弃，与“配置驱动、失效保留并报错”冲突。
   - **Windows 调度缺失**：`locate.ts` 的 `PATHEXT` 仅匹配 `.COM;.EXE;.BAT;.CMD`，不包含 `.ps1`；`pty-session.ts` 仅调用裸 `pty.kill()`。
   - **竞品排除**：`tday` 实际使用非标准自定义限制性协议；`agent-term` 明确依赖 WSL 与多窗口。

2. **作者声称证据（需存疑验证）**
   - Workbench README 声称在 Windows 11 日常开发并支持三款 CLI；Tabby 宣称成熟终端生态与多平台配置能力。这些属于设计目标与体验宣称，未证明能在严苛的“纯粹透传”约束下稳定运行。

3. **本机未实测证据（当前已知盲区）**
   - 本机 `codex.ps1` 是否在同目录具备可被 `cmd.exe` 调用的 `.cmd`/`.bat` 垫片（shim）。
   - Windows 环境下裸 `pty.kill()` 能否彻底收割 CLI 派生的深层子进程树（是否存在僵尸进程/文件锁死）。
   - 大输出流并发下，ws/pty 链路在本机的真实内存与背压表现。

### 二、 桌面壳（Electron）包装本机服务的潜在风险

将“Node 环回服务 + Electron 壳”组合时，存在三项不可忽略的工程问题：
1. **进程孤儿与级联退出**：Electron 主进程崩溃或强制关闭时，若未绑定 Windows Job Object（作业对象），后台 Node 子服务与 node-pty 生成的 CLI 树极易静默残留，导致端口占用与环境锁死。
2. **本地网络阻断与防火墙弹窗**：即便绑定 `127.0.0.1`，Windows Defender 或企业安全软件仍可能拦截无签名的 Node 动态端口监听，触发弹窗干扰用户。
3. **双重启动时序与重连竞态**：桌面壳启动时，前端加载若快于底层 Express 监听就绪，会导致初始握手失败，需增加严格的健康探活与就绪通知机制。

### 三、 最小验证关卡（Kill Switch 准则）

在写任何桌面壳代码前，按顺序执行三个“一票否决”关卡：

- **关卡 1（侵入度评估，限时半天）**：检查能否仅通过配置或极少代码屏蔽 Workbench 的历史恢复、自动日志注入、状态钩子和权限参数。**红线**：若必须重构其核心 `terminal-registry` 且改动扩散至全局，立即停止 fork。
- **关卡 2（本机调度与生命周期实测）**：验证 node-pty 在本机对 `codex.ps1`（或包装垫片）的拉起能力与独立 cwd 隔离；实测退出时子进程树释放是否彻底。**红线**：若进程树泄漏且无法通过简单脚本收割，原 session 模块不可用。
- **关卡 3（Mock 协议打通）**：基于 `pnpm demo` 挂载“会话定义真源”，验证运行代号（Generation ID）防迟到逻辑和错误路径高亮。

### 四、 共识与选型微调建议

1. **坚持两级备选策略**：以 Workbench 作为**协议与前后端通信模板**。一旦触发关卡红线，不转入沉重的 Tabby 插件开发，而是直接提取其成熟的**前端 xterm 封装 + 后端最小 node-pty 通信片段**，收敛为一个纯粹的本地单体 Electron 桌面薄应用。
2. **首版严禁读写历史文件**：启动参数一律走显式传参；路径查找显式增加对 PowerShell 脚本/原生别名的补丁，确保真实接入时不破坏用户原有的 CLI 认证环境。
